## 1. 이번 주 학습 주제

> 8월 4주간의 이론을 **실제 코드에 적용하는 첫 주간**. 본인이 소유·관리하는 코드베이스를 대상으로 **비밀 의존 분기 / 비밀 의존 메모리 인덱스 / 조기 반환 비교** 3종 패턴을 감사하고, 발견된 비교 경로를 상수시간 비교로 교체한 뒤 **생성 어셈블리를 직접 열어 분기가 실제로 제거됐는지** 확인했다. 이어 `dudect` 방식의 Welch t-검정 하네스를 만들어 **교체 전후의 실행시간 분포 차이가 통계적으로 사라지는지** 정량 비교했고, 8월 4주차에 미완으로 남겼던 **DFA on AES 마지막 라운드 키 복구식 유도**를 마무리해 소프트웨어 결함 시뮬레이션으로 검증했다. 이번 주부터 AI 도구는 **Reviewer / Debugger / Tutor** 역할로만 쓰고, AI가 내놓은 판단은 예외 없이 직접 실행·관측해 확인하는 절차를 고정했다.

## 2. 학습 내용 요약

### (황준하) 감사 대상과 범위 — 먼저 경계를 명확히 했다

감사 대상은 **본인이 작성·소유한 개인 프로젝트 코드와 격리 랩 환경**으로 한정했다. 타인의 운영 시스템이나 제3자 서비스는 대상에 넣지 않았고, 모든 측정은 로컬 장비에서만 수행했다. 이번 주 작업의 성격상 이 경계를 먼저 못 박아 두는 게 중요하다고 봤다.

감사 절차는 3단계로 설계했다.

1. **기계적 1차 스크리닝** — `memcmp` / `strcmp` / `==` 기반 바이트열 비교, 인덱스가 비밀에서 파생되는 룩업, 비밀 값을 조건으로 쓰는 `if`·`switch`·삼항 연산자를 정규식으로 훑는다. 재현성을 위해 grep 패턴 자체를 스크립트로 남겼다.
2. **수동 판정** — 1차 결과 대부분은 오탐이다. 비교 대상이 *공격자에게 이미 알려진 값*(예: 상수 매직넘버, 공개 식별자)이면 타이밍이 새도 의미가 없다. 그래서 **"이 값이 새면 무엇이 무너지는가"** 를 한 줄로 적어 남길지 버릴지 판정했다.
3. **증거 수집** — 남긴 항목마다 어셈블리와 타이밍 분포라는 두 가지 증거를 붙인다. 8월 3주차에 "소스 수준 상수시간성은 보증이 아니다"라는 걸 겪었기 때문에, 이번에는 처음부터 증거 없이는 판정하지 않기로 했다.

핵심은 **위협 모델을 먼저 쓰는 것**이었다. 타이밍 채널은 "공격자가 같은 입력에 대해 반복 측정할 수 있는가"가 성립 조건인데, 1회성 오프라인 검증 경로는 아무리 조기 반환이어도 실질 위험이 낮다. 반대로 외부에서 반복 호출 가능한 검증 엔드포인트는 바이트 단위 복구의 표준 대상이다. 이 구분을 먼저 하지 않으면 감사 결과가 전부 "고쳐야 함"이 되어 우선순위가 사라진다.

### (황준하) 패턴 1 — 비밀 의존 조기 반환 비교

가장 많이 나온 패턴이고, 8월 3주차에 이론으로 정리했던 `memcmp` 조기 반환이 실제 코드에서 그대로 나왔다.

| 발견 위치 유형 | 비교 대상 | 반복 호출 가능성 | 판정 |
|---|---|---|---|
| 세션/인증 토큰 검증 | 저장된 토큰 vs 제출된 토큰 | 높음 | **수정 대상** |
| HMAC/서명 검증 | 계산한 태그 vs 첨부된 태그 | 높음 | **수정 대상** |
| 초대·재설정 코드 검증 | 발급 코드 vs 입력 코드 | 높음(코드 길이가 짧아 더 위험) | **수정 대상** |
| 내부 설정 파일의 매직 헤더 비교 | 공개 상수 | 해당 없음 | 대상 제외 |
| 로그 태그 문자열 비교 | 비밀 아님 | 해당 없음 | 대상 제외 |

**왜 조기 반환이 치명적인가**를 다시 정리하면, 공격자의 탐색 공간이 곱셈에서 덧셈으로 바뀌기 때문이다. n바이트 태그를 전수 탐색하면 `256^n` 이지만, 접두사 일치 길이에 비례해 시간이 늘어나는 오라클이 있으면 바이트마다 256회씩 총 `256 × n` 회로 끝난다. 32바이트 HMAC이면 `2^256` 이 8192회가 된다. 이 숫자 차이가 "느린 네트워크라 어차피 안 된다"는 반론을 무력화하는 지점이다 — 측정 잡음은 반복 횟수로 평균화되지, 탐색 공간을 늘려 주지는 않는다(Brumley–Boneh 2003의 요지).

한 가지 실무적으로 배운 것은, **길이 비교가 먼저 오는 경우도 유출**이라는 점이다. `if (len(a) != len(b)) return false;` 는 비교 내용보다 길이를 먼저 흘린다. 태그처럼 길이가 고정된 값이면 문제가 없지만, 길이 자체가 비밀의 일부인 경우(예: 가변 길이 비밀)에는 별도 고려가 필요하다. 이번 대상에서는 전부 고정 길이라 길이 검사를 상수시간 비교 앞에 두는 것으로 정리했다.

### (황준하) 패턴 2 — 비밀 의존 분기

조기 반환보다 찾기 어려웠다. 형태가 일정하지 않기 때문이다.

- **직접형**: `if (secret_flag) { ... } else { ... }` — 양 분기의 실행 비용이 다르면 그대로 유출.
- **간접형**: 비밀 값의 유효성 검사에서 실패 시에만 로깅·정리 루틴이 도는 경우. 실패 경로가 성공 경로보다 명백히 무겁다.
- **루프 종료 조건형**: 비밀 값의 자릿수·유효 바이트 수만큼만 도는 루프. 반복 횟수 자체가 비밀이다.
- **예외/에러 경로형**: 8월 3주차의 패딩 오라클과 같은 구조. 에러 메시지를 통일해도 **처리 시간이 다르면 오라클이 남는다.**

분기를 산술로 바꾸는 기법은 8월에 정리한 그대로 썼다. 마스크 생성 `mask = -(uint64_t)(cond & 1)` 로 전부 1 또는 전부 0을 만들고 `out = (a & mask) | (b & ~mask)` 로 선택한다. 다만 이번에 새로 확인한 것은, **`cond` 자체를 만드는 과정이 이미 분기일 수 있다**는 함정이다. `cond = (x == y)` 를 컴파일러가 `setcc` 로 내면 상수시간이지만, 복합 조건이면 단축 평가(short-circuit)가 분기를 만든다. `&&` 를 `&` 로 바꾸는 사소한 수정이 실제로 어셈블리를 바꿨다.

### (황준하) 패턴 3 — 비밀 의존 메모리 인덱스

8월 3주차의 AES T-table 공격이 정확히 이 패턴이다. 실제 코드에서 찾은 형태는 세 가지였다.

- **룩업 테이블 인덱스** — hex/Base64 디코더의 문자→값 변환 테이블. 입력이 비밀(예: 비밀키의 hex 표현)이면 접근 인덱스가 비밀에 의존한다.
- **비밀 길이에 의존한 버퍼 슬라이싱** — 접근하는 캐시 라인 수가 달라진다.
- **조건부 조기 `break` 가 있는 배열 순회** — 패턴 1·2의 혼합형.

여기서 **실용적 타협을 기록으로 남겼다.** 문자 변환 테이블을 산술 변환(비교·마스크 조합)으로 바꾸면 상수시간이 되지만 코드가 눈에 띄게 느려지고 가독성도 떨어진다. 이번 주에는 **위험 평가만 적어 두고 교체는 보류**했다. 이유는 ① 해당 디코더가 외부에서 반복 호출되는 경로에 있지 않고 ② 관측 해상도가 캐시 라인(64B)인데 테이블이 256바이트라 4개 라인에 걸쳐 있어 얻을 수 있는 정보가 상위 2비트 수준이며 ③ 같은 프로세스 내에서 Flush+Reload를 걸 수 있는 공격자라면 이미 더 직접적인 경로가 있기 때문이다. **고칠 수 있는데 안 고친 항목을 "고쳤다"로 적지 않기 위해** 이 판단 근거를 그대로 남겼다.

### (황준하) 상수시간 비교로 교체 — 무엇으로 바꿨나

직접 구현보다 **검증된 라이브러리를 쓰는 쪽이 원칙**이라고 결론냈다.

| 언어 | 선택 | 이유 |
|---|---|---|
| Go | `crypto/subtle.ConstantTimeCompare` | 표준 라이브러리, 어셈블리 수준 검증이 되어 있음 |
| Rust | `subtle` 크레이트의 `ConstantTimeEq` | 최적화 배리어(`black_box` 계열)를 명시적으로 넣음 |
| C | 직접 작성(누적 XOR-OR) + `volatile` 배리어 | 표준 라이브러리에 없음, BearSSL 문서의 관용구를 따름 |

C에서 직접 작성한 비교의 골자는 8월에 정리한 그대로다. 두 버퍼를 바이트마다 XOR해 누적 OR하고, 루프가 끝난 뒤 **한 번만** 0인지 판정한다. 중간에 어떤 분기도, 어떤 조기 탈출도 없다. 반환값도 `diff == 0` 같은 비교 대신 `(diff - 1) >> 8` 류의 산술로 뽑았다. 다만 **직접 작성한 C 버전은 어셈블리 확인 전까지 상수시간이라고 부르지 않기로** 했고, 실제로 그게 옳았다(아래).

라이브러리를 쓰기로 한 진짜 이유는 성능이나 편의가 아니라 **최적화 배리어 관리**다. 컴파일러는 "값이 어차피 불린 하나로 수렴한다"는 걸 알면 루프를 조기 탈출로 되돌릴 권한이 있다. 표준·검증 라이브러리는 그걸 막는 장치를 이미 안에 넣어 두었다.

### (황준하) 생성 어셈블리로 분기 제거 확인 — 이번 주에서 가장 배운 부분

절차는 단순하다. 최적화 레벨별로 어셈블리를 뽑아 **비교 함수 본문에 조건 분기 명령(`je`/`jne`/`jb` 등)이 남아 있는지** 본다. 남아 있으면 상수시간이 아니다. 남아 있지 않고 `cmov`·`sete`·비트연산만 있으면 최소한 명령열 수준에서는 통과다.

확인하며 정리한 관찰들.

- **`-O0` 에서 분기가 있는 건 문제가 아니다.** 어차피 배포 빌드가 아니다. 판정은 **실제 배포에 쓰는 플래그 조합**으로 해야 한다.
- **최적화 레벨이 올라갈수록 좋아지지도, 나빠지지도 않는다.** 방향이 일정하지 않다. `-O2` 에서 `cmov` 로 잘 내려가던 코드가 다른 함수에 인라인되면서 주변 문맥 때문에 분기로 바뀌는 경우를 봤다. 그래서 **함수 단독이 아니라 호출부까지 인라인된 상태의 어셈블리**를 봐야 한다.
- **LTO(링크 타임 최적화)가 켜져 있으면 컴파일 단계 어셈블리만으로는 결론이 안 난다.** 최종 바이너리를 역어셈블해서 확인해야 한다. 이번에 처음 겪었고, 중간 산출물만 보고 "통과"라고 적을 뻔했다.
- **`cmov` 가 있다고 완전히 안심할 수는 없다.** `cmov` 자체는 상수시간이지만, 8월 4주차에 본 GoFetch/Hertzbleed처럼 하드웨어 계층이 전제를 깨는 경우가 남는다. 어셈블리 확인은 **필요조건이지 충분조건이 아니다.**

결과적으로 대부분의 경로는 통과했지만, **한 곳은 끝내 분기를 없애지 못했다.** 비교 함수 자체는 깨끗한데, 그 결과를 받아 처리하는 **호출부의 제어 흐름**이 성공/실패에 따라 크게 갈려서 전체 응답 시간에 차이가 남는다. 비교만 상수시간으로 만든다고 끝이 아니라는 뜻이다. 이건 다음 주로 넘겼다.

### (황준하) `dudect` 방식 t-검정 — 교체 전후 정량 비교

`dudect`(Reparaz et al., DATE 2017)의 아이디어는 **코드를 분석하지 않고 실행시간 분포만으로 상수시간성을 판정**하는 것이다. 정적 분석과 달리 컴파일러·CPU가 실제로 만들어 낸 결과를 본다는 게 장점이다.

**절차**

1. 입력을 두 클래스로 나눈다. **fix 클래스**(모두 동일한 고정 입력)와 **random 클래스**(매번 새 랜덤 입력).
2. 두 클래스를 **무작위 순서로 번갈아** 실행하며 각 실행의 사이클 수를 `rdtscp` 로 잰다. 순서를 섞는 게 핵심이다 — 클래스별로 몰아서 측정하면 캐시 워밍업·주파수 변화·열 상태 같은 시간에 따른 드리프트가 그대로 클래스 차이로 둔갑한다.
3. 전처리: 상위 꼬리를 자르는 **크로핑(cropping)**. 인터럽트·컨텍스트 스위치는 시간을 늘리기만 하므로(8월 3주차의 관찰), 여러 백분위수 임계로 잘라 각각 검정한다.
4. 두 클래스 표본에 **Welch's t-test**(등분산을 가정하지 않는 t-검정)를 적용한다.
5. 판정: `|t|` 가 임계값을 넘으면 "상수시간이 아니다". dudect 구현이 관용적으로 쓰는 임계값은 **4.5 근처**다.

**중요한 해석 규칙**을 따로 적어 뒀다. 이 검정은 **비상수시간을 입증할 수는 있어도 상수시간을 증명하지는 못한다.** `|t|` 가 작다는 건 "이 측정 조건에서 이 표본 수로는 차이를 검출하지 못했다"일 뿐이다. 그래서 결과를 "상수시간임이 확인됨"이 아니라 **"이 환경·이 표본 수에서 유의한 차이가 검출되지 않음"** 으로 적기로 했다.

**결과(정성)**

- 교체 **전** 취약 비교: 반복 실행 전부에서 `|t|` 가 임계값을 크게 초과했다. 표본이 쌓일수록 `t` 가 단조 증가하는 전형적인 패턴이 나왔다 — 진짜 차이가 있을 때의 모양이다.
- 교체 **후** 상수시간 비교: 같은 하네스·같은 표본 수에서 `|t|` 가 임계값 아래에 머물렀고, 표본을 늘려도 증가 추세가 나타나지 않았다.
- 다만 **측정 환경 통제가 불완전했다.** 노트북에서 돌린 탓에 터보 부스트와 열 스로틀링을 완전히 고정하지 못했고, 일부 실행 회차에서 `|t|` 가 임계값 근처까지 튀었다. 그 회차들은 크로핑 백분위수를 바꾸면 임계 아래로 내려갔는데, **전처리 파라미터에 따라 결론이 흔들린다는 것 자체가 환경 통제가 부족하다는 신호**라고 판단했다. 구체적인 `t` 값은 환경 의존이 크다고 보고 이 보고서에 수치로 남기지 않았다.

### (황준하) DFA on AES 마지막 라운드 키 복구식 유도 — 8월 미완분 마무리

8월 4주차에 오류 전파 패턴까지만 확인하고 넘긴 부분이다. 두 가지 모델로 유도했다.

**모델 A — 마지막 라운드 SubBytes 직전에 1바이트 오류**

AES-128의 마지막 라운드(10라운드)에는 MixColumns가 없다. 따라서 암호문 바이트는

`C_i = SBox(X_i) ⊕ K10_i`

(ShiftRows는 바이트 위치의 순열이므로 인덱스 대응만 맞추면 된다.) 오류가 주입된 상태 `X'_i = X_i ⊕ a` 에 대해

`C'_i = SBox(X_i ⊕ a) ⊕ K10_i`

두 식에서 `K10_i` 를 소거하면

`SBox⁻¹(C_i ⊕ K10_i) ⊕ SBox⁻¹(C'_i ⊕ K10_i) = a`

`a` 를 모르면 256개 후보를 다 넣어야 하지만, **`K10_i` 후보 256개 × `a` 후보 255개** 중 식을 만족하는 쌍만 남는다. 한 쌍의 (정상, 오류) 암호문으로 해당 키 바이트 후보가 크게 줄고, **오류 위치가 같은 (정상, 오류) 쌍을 하나 더 얻으면** 교집합으로 대개 유일해진다. 오류가 한 바이트만 번지므로 이 모델은 유도는 쉬운데 바이트당 쌍이 필요해 전체 16바이트를 얻으려면 주입 횟수가 많다.

**모델 B — 9라운드 MixColumns 입력에 1바이트 오류 (Piret–Quisquater 계열)**

훨씬 효율적인 쪽이다. 9라운드 MixColumns 입력의 한 바이트에 오류 `a` 가 들어가면, MixColumns의 열 연산 때문에 **같은 열의 4바이트로 퍼지고**, 그 차분 벡터는 MixColumns 행렬의 한 열에 `a` 를 곱한 형태 — 즉 오류 바이트 위치에 따라 `(2a, a, a, 3a)` 의 회전형 중 하나로 **고정된다.** 이후 ShiftRows가 이 4바이트를 서로 다른 열로 흩뿌리고, 마지막 라운드는 MixColumns가 없으므로 더 번지지 않는다. 결과적으로 **암호문의 4바이트만 달라진다.**

그 4바이트 위치를 `i1..i4`, 대응 차분을 `δ1..δ4` 라 하면, 각 위치마다

`SBox⁻¹(C_ij ⊕ K10_ij) ⊕ SBox⁻¹(C'_ij ⊕ K10_ij) = δ_j(a)`

가 성립하고, `δ_j` 들이 하나의 미지수 `a` 로 묶여 있다는 게 핵심이다. `a` 를 255개 후보로 고정하면 4개 식이 독립적으로 각 키 바이트를 걸러 내므로, **단순 곱 `2^32` 이 아니라 `255 × (걸러진 소수 후보)` 수준으로 축소**된다. 한 번의 오류 주입으로 `K10` 의 4바이트가 소수 후보로 줄고, 서로 다른 열을 겨냥한 오류를 몇 번 더 주입하면 `K10` 16바이트가 확정된다. `K10` 이 확정되면 **AES 키 스케줄을 역으로 돌려 원래 마스터 키를 복원**할 수 있다(키 스케줄은 가역이다).

**검증 방법 — 물리 장비 없이**

실제 결함 주입 장비가 없으므로, **본인이 작성한 AES 구현에 소프트웨어적으로 오류 바이트를 주입**해 정상/오류 암호문 쌍을 만들고, 위 유도식으로 후보 집합을 계산해 **정답 `K10` 이 후보 안에 들어 있는지** 확인하는 방식으로 검증했다. 유도가 맞다면 후보 집합은 반드시 정답을 포함해야 하고, 실제로 포함됐다. 다만 이건 **유도식이 맞다는 확인이지, 물리적 결함 주입이 가능하다는 확인은 아니다.** 클럭/전압 글리칭으로 원하는 라운드의 원하는 바이트에 오류를 넣는 것은 별개의 공학 문제고, 여전히 미경험 영역이다.

### (황준하) AI 활용 방식 — 역할을 고정하고 결과는 직접 검증

스터디 원칙대로 AI를 도구 역할로만 썼고, 이번 주에 실제로 어떻게 쓰였는지 기록한다.

| 역할 | 실제 사용 | 검증 방법 | 결과 |
|---|---|---|---|
| **Reviewer** | 상수시간 교체 패치 diff를 통째로 넣고 "남아 있는 비밀 의존 제어 흐름"을 지적받음 | 지적받은 위치를 직접 어셈블리로 확인 | 호출부 제어 흐름 차이 1건은 **유효한 지적**, 나머지 2건은 오탐(공개 상수 비교) |
| **Debugger** | dudect 하네스가 상수시간 버전에서도 계속 유의 결과를 내는 원인 질의 | 제시된 가설을 하나씩 코드에서 확인·재현 | 원인은 **클래스 배정을 무작위화하지 않은 것**. 수정 후 재현 |
| **Tutor** | Welch t-검정과 Student t-검정의 차이, 크로핑이 통계적으로 정당한 이유 | 소표본/대표본을 직접 만들어 두 검정 결과 비교 | 등분산 가정이 깨지는 조건을 직접 재현해 이해 |

**AI 판단을 직접 반증한 사례가 하나 있었다.** 직접 작성한 C 비교 함수를 넣고 물었을 때 "분기가 없어 상수시간"이라는 답을 받았는데, 실제 배포 플래그로 빌드해 역어셈블해 보니 조기 탈출이 남아 있었다. **소스만 보고 판단하는 건 AI든 사람이든 동일한 한계가 있다**는 8월 3주차의 교훈이 그대로 반복됐다. 이번 주 이후로는 AI의 상수시간 판정은 어셈블리 확인 전까지 "가설"로만 취급한다.

## 4. 주요 논의 / Q&A

- **이론 4주 뒤 첫 실습 주간에서 가장 크게 달라진 점은 무엇인가.** 8월에는 "조기 반환 `memcmp` 는 위험하다"가 명제였는데, 실제로 감사해 보니 **위험한 것과 위험하지 않은 것을 가르는 기준이 코드가 아니라 위협 모델**이었다. 같은 `memcmp` 라도 공격자가 반복 호출할 수 없으면 실질 위험이 없고, 짧은 초대 코드처럼 탐색 공간이 작으면 오히려 HMAC보다 급하다. 이론 단계에서는 보이지 않던 우선순위 문제가 실습에서 바로 나왔다.
- **소스 수준 상수시간성과 어셈블리 수준 상수시간성의 간극이 실제로 얼마나 컸는가.** 컸다. 특히 **LTO**가 문제였다. 컴파일 단계 어셈블리가 깨끗해도 링크 시점 인라인·최적화로 제어 흐름이 다시 바뀔 수 있어서, 중간 산출물만 보면 잘못된 결론에 도달한다. 이번에 절차를 "배포와 동일한 플래그 + 최종 바이너리 역어셈블"로 못 박았다.
- **비교 함수만 상수시간으로 만들면 충분한가.** 충분하지 않다는 게 이번 주 결론이다. 비교가 상수시간이어도 **그 결과를 받아 처리하는 경로가 성공/실패에 따라 다르면** 전체 응답 시간에 차이가 남는다. 8월 3주차의 패딩 오라클 원리(에러 메시지를 통일해도 처리 시간이 다르면 오라클)와 정확히 같은 구조다. 결국 **상수시간은 함수의 속성이 아니라 요청 처리 경로 전체의 속성**이다.
- **`dudect` 의 t-검정 결과를 어디까지 신뢰해도 되는가.** "상수시간이 아니다"는 결론은 강하게 받아들일 수 있지만, **"상수시간이다"는 결론은 이 검정으로 나오지 않는다.** 귀무가설 검정의 구조상 검출 실패가 곧 부재의 증명은 아니기 때문이다. 표본 수, 측정 해상도, 환경 잡음이 모두 검출력을 좌우하고, 실제로 크로핑 백분위수를 바꿨더니 경계 회차의 결론이 뒤집혔다. 그래서 결과 표현을 "유의한 차이가 검출되지 않음"으로 고정했다.
- **환경 통제를 어디까지 해야 측정이 의미를 갖는가.** 이번에 통제한 것은 코어 고정 정도고, 주파수 고정은 실패했다. 8월 4주차에 본 **Hertzbleed**가 여기에 직접 걸린다 — DVFS가 살아 있으면 소비 전력 차이가 주파수 차이로, 다시 시간 차이로 바뀌므로 **측정 환경 자체가 채널을 만든다.** 즉 주파수를 고정하지 못한 상태의 측정은 "상수시간 코드인데도 시간 차이가 관측될 수 있는" 조건을 포함한다. 다음 주 이후 측정에서는 환경 통제를 별도 체크리스트로 관리하기로 했다.
- **DFA 유도를 소프트웨어 시뮬레이션으로 검증한 것을 "검증"이라 부를 수 있는가.** 부분적으로만 그렇다. **수학적 유도가 맞다는 것은 확인**됐다 — 후보 집합이 정답을 포함했고, 키 스케줄 역산으로 마스터 키까지 복원됐다. 하지만 **물리적 결함 주입의 실현 가능성은 전혀 확인되지 않았다.** 원하는 라운드의 원하는 바이트에 단일 바이트 오류만 넣는 것은 글리칭 파라미터 탐색이라는 별개의 공학 문제이고, 장비도 경험도 없다. 두 가지를 섞어서 "DFA 공격을 재현했다"고 쓰지 않도록 주의했다.
- **AI를 Reviewer로 쓸 때의 실제 유용성과 한계.** 유용했던 건 **넓게 훑는 일**이었다 — 패치 diff에서 놓친 호출부를 하나 짚어 준 건 실제 가치가 있었다. 한계는 **실행 결과에 접근하지 못한다는 것**이다. 소스만 보고 "상수시간"이라고 판정했지만 실제 배포 빌드에서는 분기가 남아 있었다. 결국 AI의 역할은 *후보를 넓히는 것*이고, *판정은 실행과 관측*이 한다. 이 분업을 이번 주에 절차로 고정했다.

## 8. 특이사항

- **어셈블리 확인이 1건에서 통과하지 못했다.** 비교 함수 자체는 깨끗하지만 호출부 제어 흐름이 성공/실패에 따라 갈려 전체 응답 시간에 차이가 남는다. "상수시간 비교로 교체 완료"라고만 적으면 사실과 다르므로 미해결로 남긴다.
- **측정 환경 통제 실패.** 노트북 환경에서 터보 부스트·열 스로틀을 고정하지 못해 `dudect` 결과가 회차마다 흔들렸다. 구체적인 `t` 수치는 환경 의존이 커서 본문에 남기지 않았고, 다음 측정 주간(9월 3주차) 전에 환경 통제 체크리스트를 먼저 만들기로 했다.
- **비밀 의존 룩업 테이블은 의도적으로 교체하지 않았다.** hex/Base64 디코더의 변환 테이블이 비밀 의존 인덱스에 해당하지만, 호출 경로·관측 해상도·공격자 전제를 따져 보류했다. 고칠 수 있는데 안 고친 항목이므로 판단 근거를 그대로 남긴다.
- **DFA는 유도와 소프트웨어 검증까지만이다.** 수학적 유도가 맞다는 것과 물리적 결함 주입이 가능하다는 것은 별개이며, 후자는 전혀 확인되지 않았다.
- **AI 판정을 직접 반증한 사례가 나왔다.** 소스만 보고 "상수시간"이라고 한 판정이 실제 배포 빌드 역어셈블에서 뒤집혔다. AI는 후보를 넓히는 데 쓰고 판정은 실행·관측으로 한다는 원칙을 절차에 명시했다.
- **미팅 일시 미확인.** `2026/9/` 로 월까지만 기재했다.
