## 1. 이번 주 학습 주제

> **커버트 채널 심화** — 지난주 정립한 정의 위에 실제 채널 구현을 얹는 주간. 로컬 저장/타이밍 채널 사례, 네트워크 프로토콜 헤더·타이밍 기반 커버트 채널(IP/TCP/ICMP/DNS/HTTP), 에어갭(air-gap) 환경을 우회하는 물리 커버트 채널, 그리고 잡음 있는 채널에서 실제로 데이터를 실어 나르기 위한 **동기화·프레이밍·오류정정** 과 이에 대응하는 **탐지·정규화 방어**

## 2. 학습 내용 요약

### (황준하) 1. 로컬 커버트 채널 — OS 자원을 비트로 쓰기

지난주의 SRM(Shared Resource Matrix) 관점을 실제 자원에 적용해 본 결과를 정리.

**저장 채널(clock 불필요)**

| 자원 | 송신(M) 방법 | 수신(R) 방법 | 대략 대역폭 |
|---|---|---|---|
| 파일 존재 여부 | 특정 경로 파일 생성/삭제 | `stat()` 성공/실패 | 낮음, 매우 노이즈 적음 |
| 파일 락(lock) | `flock()` 획득/해제 | 락 시도의 즉시 실패 여부 | 중간 |
| 디스크 여유 블록 | 대용량 파일 할당/해제 | `statfs()` 잔여 용량 | 낮음(잡음 큼) |
| 프로세스 테이블 / PID | fork로 PID 소진 | PID 번호 관측 | 낮음 |
| inode·파일 디스크립터 수 | fd 다량 점유 | 자기 fd 할당 실패 | 낮음 |
| `errno` / exit code | 의도적 실패 유발 | 반환값 관측 | 낮음 |

**타이밍 채널(clock 필요)**

- **CPU 스케줄링 채널**: 송신자가 자기 타임슬라이스를 *전부 쓰거나*(1) *즉시 yield 하거나*(0), 수신자는 자기 루프의 진행량(반복 횟수)을 시계로 재서 비트를 복원. Lampson 1973의 원조 예시와 동일한 구조.
- **버스/메모리 컨트롤러 경합**: 송신자가 대량 메모리 접근을 폭주시켜 수신자의 메모리 지연을 늘림. 코어가 달라도 동작한다는 점이 중요(공유 자원이 코어 밖에 있음).
- **디스크 암 위치**: 송신자가 특정 실린더로 헤드를 이동시켜 수신자의 seek time을 변조. HDD 시대의 고전 사례, SSD에서는 사실상 소멸.

핵심 관찰: **로컬 커버트 채널은 "격리되어 있다고 믿는 두 프로세스"가 사실 수십 개의 자원을 공유한다는 사실을 드러낸다.** 하나를 막아도 다른 자원이 남는다는 점에서 근본적으로 두더지 잡기(whack-a-mole) 성격을 갖는다.

### (황준하) 2. 네트워크 커버트 채널 — 헤더 필드 전수 조사

이번 주 과제로 IP/TCP 헤더 필드를 훑고 커버트 채널 적합성을 정리했다. 판단 기준은 **① 실을 수 있는 비트 수, ② 정상 트래픽에서의 엔트로피(높을수록 은닉이 쉬움), ③ 중간 장비의 정규화(normalization)로 소실되는가**.

| 필드 | 가용 비트 | 정상 엔트로피 | 정규화 취약성 | 비고 |
|---|---|---|---|---|
| IP Identification (IPID) | 16 | 높음(OS별로 랜덤/순차) | 중간 | 고전적 1순위 후보. 순차 IPID OS에서는 이상 탐지 쉬움 |
| IP TTL | 8(실제 1~2) | 낮음 | **높음** — 라우터가 감소시킴 | 값 자체보다 "홀짝" 등 1비트 인코딩만 현실적 |
| IP Flags(DF/MF) | 1~2 | 매우 낮음 | 높음 | 비트 수 극소, 탐지 쉬움 |
| IP Fragment Offset | 13 | 낮음(대개 0) | 높음 | 비정상 트래픽으로 눈에 띔 |
| IP ToS / DSCP / ECN | 6~8 | 낮음 | **높음** — 재작성 흔함 | 사내망 한정 |
| IP Options | 가변(큼) | 매우 낮음 | 매우 높음 — 대개 폐기 | 대역폭 크지만 생존율 낮음 |
| TCP ISN(초기 시퀀스 번호) | 32 | **매우 높음**(암호학적 랜덤) | 낮음 | 은닉성 최상. 다만 연결당 1회 → 대역폭 낮음 |
| TCP Timestamp(TSval) 하위 비트 | 1~4 | 높음 | 중간 | 정밀도 잡음에 섞기 좋음 |
| TCP Urgent Pointer | 16 | 매우 낮음(대개 0) | 높음 | URG 미사용이 정상이라 눈에 띔 |
| TCP Reserved / Flags 조합 | 3~6 | 매우 낮음 | 높음 | 탐지 쉬움 |
| TCP Window Size | 16(실제 수 비트) | 중간 | 중간 | 혼잡제어와 충돌 |
| TCP Options 순서/패딩 | 가변 | 중간(OS 지문) | 중간 | 순서 자체를 인코딩 |

**프로토콜 페이로드 기반 채널**

- **ICMP 터널링** — ICMP Echo의 데이터 부분은 스펙상 임의 내용이라 그대로 페이로드를 실을 수 있다. 고전 도구 **Loki**(1996), 현대의 `ptunnel`. 대역폭이 크고 구현이 쉬워 여전히 실전에서 관측됨.
- **DNS 터널링** — 실무에서 가장 중요한 케이스. 이유는 *"방화벽이 DNS는 거의 항상 열어둔다"* 는 점.
  - 업스트림: 데이터를 Base32/Base64로 인코딩해 **서브도메인 라벨**에 실음(`<payload>.tunnel.attacker.com`). 라벨 63바이트, 전체 이름 255바이트 제약.
  - 다운스트림: TXT / NULL / CNAME / MX 레코드 응답 본문에 실음. 대역폭이 업/다운 비대칭.
  - 도구: **iodine**(NULL/TXT 등 다중 인코딩, MTU 자동 탐색), **dnscat2**(C2 지향, 세션·재전송 관리), **DNSCat/dns2tcp**.
  - 탐지 신호: 도메인당 질의 빈도 급증, 비정상적으로 긴 라벨, 높은 라벨 엔트로피, 낮은 NXDOMAIN 비율, 캐시 미스 편중, TXT 레코드 비율 이상.
- **HTTP(S) 기반** — 헤더 순서·대소문자·커스텀 헤더·쿠키·User-Agent·ETag·URL 파라미터, 그리고 도메인 프론팅. 정상 트래픽 볼륨이 커서 은닉이 쉬운 반면, TLS 안이라 네트워크 장비가 필드를 못 보는 대신 **JA3/JA4 핑거프린트, 패킷 크기·타이밍 분포** 로만 탐지 가능.

**패킷 타이밍·순서 기반(behavioral) 채널** — 필드를 전혀 건드리지 않으므로 정규화로 지울 수 없다는 점이 핵심.

- **IPD(Inter-Packet Delay) 변조**: 패킷 간격이 임계값보다 크면 1, 작으면 0. 네트워크 지터가 곧 잡음.
- **패킷 순서(reordering)**: n개 패킷의 순열로 `log₂(n!)` 비트 인코딩.
- **패킷 크기 변조**, **전송률(rate) 변조**, **패킷 손실 유도**.
- 이 계열은 **네트워크 스테가노그래피**와 사실상 연속선상에 있고, 방어는 필드 재작성이 아니라 **트래픽 셰이핑(일정 간격 강제 전송, 더미 패킷 삽입)** 이라는 훨씬 비싼 방법뿐이다.

### (황준하) 3. 에어갭 커버트 채널 — 네트워크가 아예 없을 때

물리적으로 분리된 시스템에서도 채널이 성립한다는 사례군. Ben-Gurion 대학 Mordechai Guri 팀의 연구가 대부분을 차지한다. 각 채널은 **매질 / 송신 하드웨어 / 수신 하드웨어 / 거리 / 대역폭** 으로 정리하면 구조가 잘 보인다.

| 채널 | 매질 | 송신 | 수신 | 대략 거리 / 대역폭 |
|---|---|---|---|---|
| **AirHopper** | FM 전자기파 | 디스플레이 케이블의 신호 변조 | 근처 휴대폰 FM 수신기 | 1~7 m / 수백 bps |
| **GSMem** | 셀룰러 대역 EM | 메모리 버스 접근 패턴 | 개조 휴대폰 | 수 m / 1~2 bps |
| **Fansmitter** | 음향(가청/근접) | CPU/케이스 팬 RPM 변조 | 마이크 | 수 m / 수십 bps |
| **DiskFiltration** | 음향 | HDD 액추에이터 소음 | 마이크 | 2 m / 180 bps |
| **초음파(ultrasonic)** | 18~20 kHz | 스피커 | 마이크 | 수 m / 수백 bps — 스피커 없는 PC에서도 헤드폰/버저 악용 사례 존재 |
| **BitWhisper** | 열 | CPU 부하로 발열 조절 | 인접 PC의 온도 센서 | 40 cm / **8 bit/hour** |
| **LED-it-GO** | 광학 | HDD 활동 LED 점멸 | 카메라/광센서 | 가시선 / 최대 4000 bps |
| **PowerHammer** | 전력선 전도 | CPU 부하로 소비전력 변조 | 전력선 전류 측정 | 배전반 / 10~1000 bps |
| **AIR-FI** | Wi-Fi 대역 EM | DDR 메모리 버스에서 2.4GHz 방사 | 일반 Wi-Fi 수신기 | 수 m / 수백 bps |

관찰 두 가지:
1. **대역폭 스펙트럼이 8 bit/hour ~ 4000 bps로 5자릿수 이상 벌어진다.** BitWhisper는 실용성이 거의 없지만 "열도 채널이 된다"는 존재 증명으로서 의미가 있고, LED 광학 채널은 실제 위협 수준.
2. **송신 측에는 반드시 이미 악성코드가 심겨 있어야 한다.** 즉 에어갭 채널은 초기 침투 수단이 아니라 **유출(exfiltration) 최종 단계**의 문제다. 지난주에 정리한 "커버트 채널은 송신자의 의도를 전제한다"는 정의가 여기서 그대로 확인된다.

### (황준하) 4. 잡음 있는 채널에서 실제로 데이터를 나르기

이론상 채널이 존재하는 것과 실제로 파일을 유출하는 것은 다른 문제라는 걸 이번 주에 확실히 정리했다. 필요한 요소 4가지:

1. **동기화(synchronization)** — 송수신이 심볼 경계를 공유해야 한다. 방법: 고정 클럭 합의, 프리앰블(예: `10101010`) 전송, 자기동기 부호(Manchester encoding — 전이 자체가 클럭을 실어 나름).
2. **프레이밍(framing)** — 시작/끝 구분자, 길이 필드, 체크섬. 프레임 단위 재전송이 가능해짐.
3. **오류 정정(FEC)** — 채널 오류율 p가 높을수록 필수. 단순 반복 부호(3회 다수결) → 해밍 부호 `(7,4)`(1비트 정정) → 리드-솔로몬(버스트 오류 대응). 대가는 대역폭 감소.
4. **변조(modulation)** — 이진 On/Off Keying이 기본. 대역폭을 올리려면 다심볼(예: CPU 부하를 4단계로 나눠 심볼당 2비트), 잡음에 강하게 하려면 확산(spread spectrum) 방식.

지난주 계산한 `C = 1 - H(p)` 를 여기에 대입하면, **오류율 p를 줄이는 비용(FEC 오버헤드)과 심볼 주기 T를 줄이는 이득(잡음 증가)이 정면으로 충돌**한다는 게 눈에 보인다. 실제 커버트 채널 논문의 실측 대역폭이 이론값보다 한참 낮은 이유가 여기 있다.

### (황준하) 5. 탐지와 방어

**탐지(detection)**
- 통계적 이상 탐지: 필드 값 분포의 엔트로피 측정, 정상 OS 지문과의 불일치(예: 순차 IPID여야 할 OS에서 랜덤 IPID), 프로토콜 스펙 위반.
- 타이밍 채널 탐지: IPD 분포의 규칙성/이중봉(bimodal) 형태 검출, ε-similarity, 정규화된 조건부 엔트로피 기반 지표.
- 행위 탐지: DNS 질의 빈도·라벨 길이·엔트로피 결합 룰, beaconing 주기성 탐지.
- 한계: **정상 트래픽의 자연 변동이 크면 낮은 대역폭 채널은 통계적으로 숨는다.** 탐지는 본질적으로 대역폭이 클 때만 잘 듣는다.

**방어(elimination / mitigation)**
- **트래픽 정규화(traffic normalizer / protocol scrubber)** — 게이트웨이에서 IPID 재작성, TTL 통일, 옵션 제거, 타임스탬프 재생성, 플래그 정규화. 헤더 기반 채널에는 매우 효과적이지만 **타이밍 채널에는 무력**.
- **Pump 계열(NRL Pump)** — High→Low 방향 ACK 타이밍을 랜덤화된 이동평균으로 대체해 타이밍 채널 대역폭을 정보이론적으로 제한. "제거가 아니라 대역폭 상한 설정"이라는 이 분야의 전형적 처방.
- **Fuzzy time** — 시계 해상도를 의도적으로 낮추거나 지터를 주입해 타이밍 측정을 방해. 브라우저의 `performance.now()` 해상도 축소(Spectre 대응)가 정확히 같은 아이디어.
- **자원 파티셔닝·정적 할당** — 공유 자체를 없앰. 가장 확실하지만 성능·비용 손실이 큼.
- **감사·대역폭 산정** — TCSEC B2/B3식 접근. 남은 채널을 문서화하고 임계 대역폭 이하로 유지.

핵심 결론: **커버트 채널 방어는 "제거"가 아니라 "대역폭 예산 관리"다.** 지난주 정리한 non-interference 불가능성의 실무적 귀결.

## 4. 주요 논의 / Q&A

- **Q. 헤더 기반 채널과 타이밍 기반 채널 중 실전에서 더 위험한 쪽은?**
  → 탐지·방어 관점에서는 **타이밍 채널이 훨씬 까다롭다.** 헤더 채널은 게이트웨이 정규화 한 방으로 대부분 소멸하지만, 타이밍 채널은 패킷 내용을 전혀 바꾸지 않으므로 정규화가 통하지 않고 트래픽 셰이핑이라는 값비싼 처방이 필요하다. 다만 대역폭은 헤더 채널이 훨씬 높아, "위험"의 정의(유출량 vs 탐지 회피)에 따라 답이 갈린다.
- **Q. DNS 터널링이 왜 아직도 잘 통하는가?**
  → 기술적 취약점이 아니라 **운영상의 신뢰 가정** 때문. 거의 모든 네트워크가 DNS를 무조건 허용하고, 재귀 리졸버 구조상 내부 호스트가 외부 권한 서버와 간접 통신하는 것이 *정상 동작*이다. 즉 이건 프로토콜 버그가 아니라 정책 설계의 결과다.
- **Q. 에어갭 채널은 실용적 위협인가, 학술적 호기심인가?**
  → 둘 다. BitWhisper(8 bit/hour)처럼 실용성이 없는 것도 있지만, 유출 대상이 **암호키(수백 비트)** 라면 낮은 대역폭도 충분하다는 점이 중요하다. 4000 bps급 광학 채널은 명백한 실전 위협. 다만 전제(송신 측 사전 감염 + 수신 장비의 물리적 근접)가 무거워, 표적형 공격 시나리오로 한정된다.
- **Q. 지난주 정의를 다시 적용하면 DNS 터널링은 커버트 채널인가?**
  → 그렇다. 송신자(감염 호스트)가 의도적으로 정보를 흘리고, DNS는 데이터 전송용으로 설계된 채널이 아니며, 방화벽 정책이 허용하지 않는 방향의 통신이기 때문. 반면 같은 DNS를 이용해 *제3자의 질의 패턴을 관측*해 무언가를 알아내면(DNS 캐시 스누핑) 그건 사이드 채널이다. **동일 프로토콜이 의도에 따라 양쪽 모두가 될 수 있다**는 게 이번 주에 얻은 감각.
- **"송신 → 인코딩 → 잡음 → 복호" 구조의 재사용성.** 네트워크 채널이든 에어갭 채널이든 구성이 동일하다는 점을 확인했고, 이 구조는 캐시를 매질로 쓰는 채널에도 그대로 적용된다. 특히 Flush+Reload 같은 캐시 관측 기법은 *수신기* 로서 커버트 채널과 사이드 채널 양쪽에 쓰이는 이중 용도 기술이다.

## 8. 특이사항

- **PoC 2건 중 타이밍 채널은 미완에 가깝다.** 파일 락 기반 저장 채널은 안정적으로 동작했으나, CPU 부하 기반 타이밍 채널은 스케줄러 잡음으로 오류율이 높아 실용 수준이 아니다. 다만 이론 대역폭과 실측의 괴리를 체감했다는 점에서 기록으로 남긴다.
- **에어갭 채널 대역폭 비교의 한계.** 논문마다 측정 거리·수신 장비·환경 잡음이 달라 표의 수치를 직접 비교하기 어렵다. 규모 감각 용도로만 쓰고 절대 비교에는 쓰지 않기로 했다.
- **헤더 필드 엔트로피는 문헌 값에 의존했다.** 정량 측정을 하려면 대표성 있는 정상 트래픽 캡처가 필요한데 확보하지 못했다.
- **미팅 일시 미확인.** `2026/8/` 로 월까지만 기재했다.
