# 실습 연습 가이드

주간보고서에 기록한 실습을, 발표 전에 **직접 다시 풀어 보기 위한** 문서.
각 실습에 대응하는 랩 문제와 권장 순서를 적어 둔다.

랩: `lab.anhk.net` · 카테고리 **사이드 채널 (Side Channel)**

---

## 1. 난이도 계단 점검

8월(이론)에서 9월(실습)로 넘어갈 때 단계를 건너뛴 곳이 있는지 주제 줄기별로 확인했다.
**9월 실습 항목은 모두 8월에 대응하는 선행 단계가 있다.**

| 주제 줄기 | 8월 (읽기·손계산·최소 PoC) | 9월 (실행·측정·정량화) | 대응 랩 난이도 |
|---|---|---|---|
| 캐시 타이밍 기초 | 1주 지연 실측 환경 구축 → 3주 히스토그램 | 2주 히트/미스 임계값 **절차로 고정** | easy |
| Flush+Reload | 3주 최소 PoC → 4주 수신부 재사용 검증 | 2주 수신부 재구축 → 3주 **송수신 통신 시스템**(동기화·프레이밍) | easy → medium |
| Prime+Probe | 3주 eviction set 구성 **시도(실패)** → 4주 huge page **재시도** | 3주 **재현 성공** → 채널화·용량 산출 | easy → hard |
| AES T-table | 3주 첫 라운드 인덱스 유출 **손계산** | 2주 취약 빌드 직접 작성 → 키 복구 재현(부분) | medium |
| 상수시간 | 3주 상수시간 함수 **직접 작성** + 타이밍 실험 | 1주 실코드 감사·교체 → 어셈블리 확인 → LTO → `dudect` t-검정 | hard → expert |
| 투기실행 | 4주 공식 자료 정독 + PoC 코드 **분해(읽기)** | 2주 Spectre v1 **재현(부분)**, Meltdown **재현 시도(미완)** | expert |
| 전력분석·결함주입 | 4주 CPA 시뮬레이션, 리키지 모델 오선택 실험, DFA 오류 전파 **손계산** | 1주 DFA 키 복구식 **유도 + 소프트웨어 검증** | hard |

**판정**: 8월은 읽기·손계산·최소 PoC, 9월은 실행·측정·정량화로 한 칸씩 올라간다.
9월에 선행 없이 새로 등장한 공격 기법은 없다.

**예외 1건**: 9월 4주의 **탐지·회피**는 8월에 실습 선행이 없다(8월 2주·4주의 방어 이론만 있음).
다만 탐지 대상이 3주차에 **본인이 직접 만든 채널**이므로, 대상 자체는 선행이 있다.

## 3. 권장 연습 순서

배점이 아니라 **선수관계** 기준. 앞 문제에서 만든 도구를 뒤에서 그대로 쓴다.

**1단계 — 측정 기반 (easy)**
1. `c05` 교정 — 분포를 안 주므로 **직접 재고 회차 수를 계산**한다. 이게 뒤 전부의 전제.
2. `c01` Flush+Reload — 비밀 바이트 하나로 접근된 한 줄을 찾는다.
3. `c04` 라인 해상도 — 한 라인에 네 칸이 들어가므로 교차 관측이 필요하다.
4. `c03` Prime+Probe — 피해자를 직접 못 볼 때 내 줄의 축출을 본다.
5. `c02` Evict+Time — 밀어낸 뒤 피해자 실행시간을 잰다.

**2단계 — 암호 표적 (medium)**
6. `c06` T-table 첫 라운드 — 평문을 고를 수 있으면 항상 만져지는 줄이 생긴다.
7. `c07` 마지막 라운드 — **안 만져진 줄**이 정보를 준다(역발상).
8. `c09` 은닉 채널 — 공유한 것이 캐시 라인 하나뿐인데 통신이 된다.

**3단계 — 구조 다루기 (hard)**
9. `c11` eviction set — 축출 집합을 찾는 것 **자체가** 공격이다.
10. `c16` 프리페처 — 프리페처가 공격자 관측도 오염시킨다.
11. `c15` 상수시간 감사 — 답이 키가 아니라 **판정**이다.
12. `sidechannel-keyrecovery-cpa` — 파일형. 합성 트레이스 400개에서 AES-128 키 16바이트 복구.

**4단계 — 투기실행·평가 (expert)**
13. `c17` Spectre v1 — 검사는 막았는데 캐시는 신경 쓰지 않았다.
14. `c18` Spectre v2 — v1은 조건을 뒤집고 v2는 **코드를 고른다**.
15. `c19` Meltdown — 폴트는 전달됐고 캐시는 이미 움직였다.
16. `c20` MDS — 고를 수 있는 것은 오프셋뿐이다.
17. `c22` 누출 평가 — **검정 통과는 안전 증명이 아니다.** 9월 1주의 `dudect` 작업과 직접 이어진다.

## 4. 푸는 법

컨테이너형(`○`)은 문제 페이지에서 머신을 기동하면 `http://<호스트>:<포트>` 가 뜬다.
서버가 캐시 모형을 돌리고 **접근 지연 관측치를 HTTP 로 내보내는** 구조라, 실제 하드웨어 캐시를 재는 것이 아니다.
컨테이너·공유 호스트에서 진짜 캐시 타이밍이 잡음에 묻히는 문제를 피하려고 그렇게 만들어져 있고, 대신 어디서 돌려도 같은 답이 나온다.

- `/params` 로 캐시 규격(셋·웨이·라인 크기)과 지연 분포를 먼저 확인한다.
- 문제마다 힌트가 단계별로 붙어 있다.
- 각 문제의 시간 제한은 2시간.
- 동시에 최대 3대까지 기동된다.

파일형(`◇`)은 소스와 데이터를 내려받아 로컬에서 푼다.

## 5. 기록해 둘 것

발표 때 「보고서에 부분·미완으로 적은 것」을 질문받을 수 있다. 특히:

- **9월 2주 T-table 키 복구** — 일부 키 바이트의 상위 니블만 수렴. 랩 `c06`/`c07` 에서 전체 수렴을 보고, 내 랩에서 왜 안 됐는지(잡음·프리페처·동기화) 대조해 두면 답할 거리가 된다.
- **9월 2주 Meltdown 미재현** — KPTI 활성 상태였다. 랩 `c19` 는 완화가 없는 모형이므로, **완화가 없으면 어떻게 되는지**를 보고 대조로 설명할 수 있다.
- **9월 3주 Prime+Probe 용량 산출 보류** — 회차 간 편차가 신뢰구간보다 컸다. 랩 `c11` 로 축출 집합 구성 자체를 다시 다듬으면 편차 원인을 좁힐 수 있다.
